# دوراتو | Doratou Backend

بک‌اند دوراتو برای هماهنگی دورهمی‌ها و سفرهای گروهی است. هر برنامه در یک «اکیپ» مدیریت می‌شود و اعضا می‌توانند دعوت بفرستند، وسایل را تقسیم کنند، رأی بدهند، هزینه و سهم ثبت کنند و وضعیت تسویه را ببینند.

## راه‌اندازی محلی

### ۱. پیش‌نیازها و دریافت پروژه

- Go مطابق نسخهٔ تعیین‌شده در [go.mod](go.mod). نسخهٔ این شاخه `1.26.0` است.
- Docker فعال و Docker Compose نسخهٔ ۲ با پشتیبانی از `up --wait`.
- Git و GNU Make برای دستورهای `make`. در PowerShell می‌توانید اسکریپت‌های ویندوز را مستقیم اجرا کنید.
- Bruno برای اجرای درخواست‌های نمونه. در Windows با WSL 2، Go و Make باید داخل همان توزیع در دسترس باشند. Docker نیز باید از همان توزیع قابل اجرا باشد.

از محیطی که قرار است بک‌اند را در آن اجرا کنید، مخزن را دریافت کنید. برای توسعهٔ تیمی، شاخهٔ `develop` مبناست.

<div dir="ltr">

```sh
git clone https://github.com/Doratou/Backend.git
cd Backend
git switch develop
```

</div>

اگر مخزن را از قبل دارید، دستورهای بعدی را از ریشهٔ همان مخزن اجرا کنید. قابلیت‌های مستندشده به نسخه‌ای که checkout کرده‌اید وابسته‌اند.

### ۲. تنظیم محیط

در Linux یا WSL، فایل محلی را در صورت نیاز از [.env.example](.env.example) بسازید.

<div dir="ltr">

```sh
test -f .env || cp .env.example .env
```

</div>

در ریشهٔ مخزن، معادل PowerShell را اجرا کنید.

<div dir="ltr">

```powershell
if (-not (Test-Path -LiteralPath .env)) { Copy-Item -LiteralPath .env.example -Destination .env }
```

</div>

این دو کلید را در `.env` اضافه کنید. Compose برای انتشار پورت‌های RustFS به آن‌ها نیاز دارد و فایل نمونهٔ این نسخه آن‌ها را ندارد.

<div dir="ltr">

```dotenv
RUSTFS_API_PORT=9000
RUSTFS_CONSOLE_PORT=9001
```

</div>

| تنظیم | کاربرد |
| --- | --- |
| `HTTP_DOMAIN` و `HTTP_PORT` | نمونهٔ محلی `0.0.0.0` و `8080` است. از سمت Bruno به `http://127.0.0.1:8080` درخواست بفرستید. |
| `PDB_*` | اتصال و مشخصات PostgreSQL. میزبان محلی `127.0.0.1` و پورت نمونه `15432` است. |
| `RDB_*` | اتصال Redis. میزبان محلی `127.0.0.1` و پورت نمونه `16379` است. |
| `RUSTFS_*` | اطلاعات دسترسی و نام bucket. اگر پورت API را عوض کردید، `RUSTFS_ENDPOINT` و `RUSTFS_PUBLIC_URL_PREFIX` را هم با پورت جدید تنظیم کنید. |
| `RMQ_*` | اطلاعات اتصال RabbitMQ برای صف پیام‌ها. پورت نمونهٔ AMQP برابر `5672` است. |
| `JWT_SECRET_KEY` و `INVITE_ENCRYPTION_SECRET` | کلیدهای مستقل برای JWT و رمزنگاری دعوت. مقادیر نمونه را در محیط اشتراکی با مقدار اختصاصی جایگزین کنید. |
| `SEED_USER_*`، `SEED_ADMIN_*` و `SEED_GROUP_*` | اطلاعات حساب عادی، ادمین و اکیپ نمونه در دیتابیس محلی. |
| `CAPTCHA_ENABLED` و `EMAIL_DELIVERY_ENABLED` | کپچا روی مسیرهای مربوط به احراز هویت و ارسال واقعی OTP ایمیل را کنترل می‌کنند. برای تست محلی می‌توانید هر دو را `false` تنظیم کنید. |
| `GOOGLE_*`، `OAUTH_*`، `AVALAI_*` و `WS_*` | تنظیمات ورود گوگل، همیار و WebSocket. برای ورود با رمز و تست قابلیت‌های اصلی، Google OAuth می‌تواند غیرفعال بماند. |

فایل `.env` محلی و در `.gitignore` است. اگر PostgreSQL را قبلاً با یک volume راه‌اندازی کرده‌اید، تغییر اطلاعات کاربر در `.env` کاربر قبلی دیتابیس را تغییر نمی‌دهد. تنظیمات برنامه باید با همان دیتابیس هماهنگ باشند.

### ۳. اجرای سرویس‌ها، مایگریشن و برنامه

در Linux یا WSL این سه دستور را به‌ترتیب اجرا کنید.

<div dir="ltr">

```sh
make up
go run ./cmd/migrate up
make run
```

</div>

در PowerShell با Go و Docker نصب‌شده روی ویندوز، معادل بدون GNU Make را اجرا کنید.

<div dir="ltr">

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows\up.ps1
go run ./cmd/migrate up
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows\run.ps1
```

</div>

`make up` چهار سرویس `db`، `redis`، `rustfs` و `rabbitmq` را با [Docker Compose](docker/docker-compose.yaml) روشن می‌کند و تا آماده‌شدن آن‌ها صبر می‌کند. سپس مایگریشن‌ها را روی PostgreSQL اجرا کنید. `make run` برنامه را روی میزبان می‌سازد و در ترمینال فعلی اجرا می‌کند. بعد از دریافت تغییرات دیتابیس هم دوباره `go run ./cmd/migrate up` بزنید.

`go run ./cmd/migrate up` از Goose به‌عنوان وابستگی Go استفاده می‌کند. نصب جداگانهٔ Goose فقط برای مسیرهای اسکریپتی مبتنی بر CLI مانند `make migrate-up` لازم است. برای مشاهدهٔ وضعیت مایگریشن‌ها و کانتینرها می‌توانید این دستورها را در ترمینال دوم اجرا کنید.

<div dir="ltr">

```sh
go run ./cmd/migrate status
docker compose --env-file .env -f docker/docker-compose.yaml ps
curl -i http://127.0.0.1:8080/health
```

</div>

در PowerShell برای درخواست آخر می‌توانید `curl.exe` را صدا بزنید. `GET /health` با `200 OK` و بدنهٔ `{"status":"ok"}` در دسترس بودن سرور HTTP را نشان می‌دهد. برای بررسی دسترسی به سرویس‌های زیرساختی، وضعیت Compose و پیام‌های راه‌اندازی برنامه را هم ببینید.

### ۴. توقف، workerها و دادهٔ محلی

| دستور | کاربرد |
| --- | --- |
| `make stop` | توقف برنامه و workerهایی که با اسکریپت‌های پروژه اجرا شده‌اند. |
| `make down` | توقف و حذف کانتینرهای Compose با حفظ volumeها. |
| `make workers` | ساخت و اجرای workerهای ایمیل و SMS در ترمینال جداگانه. برای SMTP صف‌شده worker ایمیل باید فعال باشد. worker پیامک در این نسخه ارسال را شبیه‌سازی و در ترمینال ثبت می‌کند. |
| `make fmt` | اجرای `gofmt` روی فایل‌های Go. |
| `make migrate-down STEPS=1` | بازگرداندن آخرین مایگریشن. به Goose CLI نیاز دارد و ممکن است داده‌های مربوط به همان مایگریشن حذف شوند. |
| `make db-reset` | حذف اسکیمای `public` در دیتابیس و اجرای دوبارهٔ مایگریشن‌ها. فقط برای دیتابیس محلی قابل‌حذف است و به Goose CLI نیاز دارد. |

برای اجرای مستقیم در PowerShell، اسکریپت متناظر را در [scripts/windows](scripts/windows) پیدا کنید. اگر ابزارها را داخل WSL نصب کرده‌اید، کل مراحل را در همان WSL اجرا کنید. از PowerShell هم می‌توانید از ریشهٔ مخزن با `wsl --exec make stop` و `wsl --exec make down` برنامه و سرویس‌ها را متوقف کنید.

## تست دستی با Bruno

1. پوشهٔ [bruno](bruno) را به‌عنوان Collection باز کنید و Environment برابر `Local` را انتخاب کنید.
2. در بخش Secrets محیط، `baseUrl` را روی `http://127.0.0.1:8080` بگذارید. اگر پورت برنامه فرق دارد، همین متغیر را هم مطابق آن تغییر دهید.
3. ابتدا `Health Check` را بفرستید. برای ورود، در `Auth / 05. Login (Identifier + Password)` ایمیل و رمز را برای **همان حساب** تنظیم کنید. می‌توانید از جفت `seedUserEmail` و `seedUserPassword` یا جفت `seedAdminEmail` و `seedAdminPassword` استفاده کنید.
4. پس از ورود موفق، کالکشن `token` و `refreshToken` را از پاسخ می‌گیرد. برای درخواست‌های محافظت‌شده از توکن دسترسی استفاده کنید. شناسهٔ اکیپ، عضو یا رکورد را از پاسخ واقعی همان دیتابیس بردارید و متغیرهای درخواست مربوط را تنظیم کنید. برای تست دو نقش هم‌زمان، دو محیط جدا با دو حساب داشته باشید.

اپلیکیشن هنگام شروع، کاربران و گروه‌های نمونه و داده‌های تست نظرسنجی و قرعه‌کشی را سید می‌کند. ایمیل و رمز حساب عادی و ادمین اصلی از `SEED_USER_*` و `SEED_ADMIN_*` می‌آیند. برای سناریوهای مالک و عضو، سید تست دستی حساب‌های `owner@test.com` و `member@test.com` را هم دارد. رمز نمونهٔ این دو حساب در [سید تست دستی](internal/infrastructure/seed/manual_test_seed.go) تعریف شده است. شناسهٔ اکیپ را از `Get User Groups` و شناسهٔ عضویت را از `Get Group Members` بگیرید تا تست روی دیتابیس‌های مختلف هم قابل تکرار باشد. رمزهای `SEED_USER_PASSWORD` و `SEED_ADMIN_PASSWORD` هنگام ساخت این دو حساب اعمال می‌شوند. سید تست دستی هنگام اجرای مجدد، رمز حساب‌های کمکی را به مقدار تعریف‌شده در کد برمی‌گرداند. [کد سیدها](internal/infrastructure/seed)

در حالت `EMAIL_DELIVERY_ENABLED=false`، کد OTP ایمیل در ترمینال بک‌اند چاپ می‌شود. برای تست SMTP واقعی، `EMAIL_DELIVERY_ENABLED=true`، `EMAIL_DELIVERY_MODE=SMTP` و اطلاعات فرستنده و SMTP را تنظیم کنید. با RabbitMQ فعال، پیام در صف قرار می‌گیرد و worker ایمیل آن را ارسال می‌کند. کد یک‌بارمصرف در Redis نگهداری می‌شود و قالب HTML، متن جایگزین و تصویر سربرگ در [قالب ایمیل OTP](internal/infrastructure/email/templates/otp) قرار دارند.

## قراردادهای مهم برای فرانت‌اند

### هویت، دوستی و صفحه‌بندی

- برای مسیر محافظت‌شده هدر `Authorization: Bearer <access_token>` بفرستید. `user_id` شناسهٔ حساب و `member_id` شناسهٔ عضویت همان حساب در یک اکیپ است. برای سهم هزینه، رأی، پرداخت و یال‌های گراف، قرارداد همان اندپوینت را برای انتخاب شناسه ملاک بگیرید.
- برای افزودن دوست، کد خود را از `GET /api/v1/users/me` بگیرید. کد دوست را با `GET /api/v1/users/by-friend-code/{friendCode}` جست‌وجو کنید و بعد از نمایش مشخصات، `data.id` را در `receiver_user_id` برای `POST /api/v1/friendships/requests` بفرستید. کد حساب از مسیر `POST /api/v1/users/me/friend-code/regenerate` قابل تعویض است. درخواست ردشده تا پایان `FRIENDSHIP_REQUEST_COOLDOWN` قابل ارسال مجدد نیست. فهرست اکیپ‌های مشترک از `GET /api/v1/friendships/{id}/mutual-groups` و با شناسهٔ رابطهٔ دوستی دریافت می‌شود.
- در فهرست‌هایی که از صفحه‌بندی مشترک استفاده می‌کنند، `page` از ۱ شروع می‌شود، `limit` به‌طور پیش‌فرض ۲۰ و حداکثر ۱۰۰ است و `pagination.total` تعداد کل آیتم‌های منطبق با فیلتر را می‌دهد. پاسخ معمول API موفق شامل `success` و `data` است. در خطا، `code` برای تصمیم‌گیری برنامه و `error` برای توضیح خطا کاربرد دارد.

### چرخهٔ اکیپ و عملیات گروهی

اکیپ از `ACTIVE` به `SETTLING` و سپس به `CLOSED` می‌رود. هنگام تسویه، پرداخت‌ها طبق قوانین خودشان قابل ثبت و بررسی‌اند و ویرایش هزینه، نظرسنجی، قرعه‌کشی و چک‌لیست فریز می‌شود. برای بستن اکیپ باید ابتدا پرداخت‌های در انتظار تعیین تکلیف شوند. اکیپ بسته برای اعضای مجاز فقط خواندنی است.

- **نظرسنجی** با `allow_multiple_choices` تعیین می‌کند کاربر چند انتخاب می‌تواند داشته باشد. درخواست `PUT .../vote` کل انتخاب نهایی را با `option_ids` دریافت می‌کند و `DELETE .../vote` همهٔ انتخاب‌های همان کاربر را پس می‌گیرد. `total_votes` تعداد انتخاب‌ها و `total_voters` تعداد اعضای رأی‌دهنده است. هویت رأی‌دهنده فقط در نظرسنجی عمومی نمایش داده می‌شود. بستن و حذف نظرسنجی با سازنده است.
- **قرعه‌کشی** حداکثر یک پیش‌نویس برای هر اکیپ دارد. سازنده می‌تواند پیش‌نویسش را ویرایش کند و هر عضو فعال می‌تواند آن را اجرا کند. در حالت `WEIGHTED` جمع درصدها دقیقاً ۱۰۰ است. برای گزینهٔ `USER`، مقدار `value` شناسهٔ کاربر است و مشخصات عمومی آن از `GET /api/v1/users/{id}` دریافت می‌شود. برای توقف گردونه روی گزینهٔ برنده از `result.index` که از صفر شروع می‌شود استفاده کنید. نتیجهٔ ثبت‌شده در تاریخچه می‌ماند.
- **چک‌لیست** برای `filter` مقادیر `all`، `claimed`، `unclaimed`، `mine` و `personal` را می‌پذیرد. `summary` و `member_claims` آمار کل فهرست را در هر صفحه و فیلتر می‌دهند. آیتم `PERSONAL` یادآوری مشترک است. عضو فعال می‌تواند آیتم آزاد یا یادآوری را حذف کند. فقط مالک می‌تواند آیتم برداشته‌شده را حذف کند و فقط خودِ فردی که آن را برداشته می‌تواند آزادش کند. با خروج یا حذف عضو، آیتم‌های او آزاد می‌شوند.

### هزینه، رسید و تسویه

- ثبت‌کنندهٔ هزینه به‌عنوان پرداخت‌کننده ثبت می‌شود. سهم‌ها می‌توانند شامل خود او و اعضای فعلی یا سابق اکیپ باشند. ورودی سهم‌ها شناسهٔ عضویت می‌گیرد. روش‌های تقسیم `EQUAL`، `EXACT`، `PERCENTAGE` و `WEIGHTED` هستند و مبلغ‌ها عدد صحیح به تومان‌اند. ویرایش و حذف با سازندهٔ فعال یا مالک فعال است. برای تغییر جزئی از `PATCH` استفاده کنید. فهرست هزینه‌ها `scope=all`، `scope=created_by_me` و `scope=owed_by_me` دارد.
- برای هزینه یا پرداخت، ابتدا فایل را با نوع مناسب `EXPENSE_RECEIPT` یا `SETTLEMENT_RECEIPT` آپلود و سپس شناسهٔ آن را در `attachment_ids` ارسال کنید. دسترسی به رسید به رکوردی که به آن متصل است وابسته است. برای نمایش تصویر پس از انقضای لینک امضاشده، جزئیات را دوباره بگیرید.
- پرداخت، ثبت یک انتقال انجام‌شده بیرون از برنامه است. پرداخت در انتظار را دریافت‌کننده تأیید یا رد می‌کند و فرستنده می‌تواند آن را پیش از پاسخ حذف کند. اعضای فعال می‌توانند سوابق تأیید و ردشده را ببینند. پرداخت در انتظار برای طرفین فعال قابل مشاهده است. اگر فرستنده خارج شود، دریافت‌کنندهٔ فعال هنوز می‌تواند پاسخ بدهد. اگر دریافت‌کننده پیش از پاسخ خارج شود، پرداخت `CANCELED` می‌شود.
- **گزارش‌ها** شامل سهم‌های بدهکار و طلبکار، گراف خام با یک یال برای هر سهم و گراف کمینهٔ تسویه هستند. سهم‌های خام عنوان هزینه را حفظ می‌کنند و عضو سابق با `is_former_member` مشخص می‌شود. گراف تسویه با پرداخت‌های تأییدشده و ماندهٔ جاری اعضای فعال به‌روز می‌شود. برنامهٔ پرداخت شخصی زیرمجموعهٔ همان گراف برای کاربر است.

### کیف پول و پرداخت آزمایشی

همهٔ مسیرهای زیر برای حساب فعال و با توکن دسترسی کار می‌کنند. مسیر قدیمی `GET /api/v1/users/me/wallet` برای خواندن موجودی در قرارداد قبلی برقرار است. صفحهٔ کیف پول اطلاعات تکمیلی را از `/api/v1/wallet/summary` می‌گیرد.

| متد و مسیر | کاربرد |
| --- | --- |
| `GET /api/v1/wallet/summary` | موجودی، مجموع خرید و مصرف و هدیه، نرخ و ارزش تقریبی و پیشرفت تکمیل پروفایل |
| `GET /api/v1/wallet/offers` | نرخ پایه، بسته‌ها و بازهٔ خرید سفارشی |
| `POST /api/v1/wallet/purchases` | خرید شبیه‌سازی‌شده با `package_id` یا `token_amount` و هدر الزامی `Idempotency-Key` |
| `GET /api/v1/wallet/transactions` | تاریخچهٔ صفحه‌بندی‌شده با فیلتر `PURCHASE`، `SPEND` یا `REWARD` |
| `GET /api/v1/wallet/transactions/{transactionID}` | جزئیات و کد پیگیری تراکنش برای نمایش رسید آزمایشی |

در دیتابیس تازه، ابتدا یک ادمین با `PUT /api/v1/admin/token-price` و بدنهٔ `{"price_toman":5000}` نرخ مثبت ثبت می‌کند. بعد از آن با حساب کاربر، پیشنهادها را بگیرید و مبلغ نهایی را با `expected_amount_toman` تأیید کنید. مثلاً با نرخ پایهٔ ۵٬۰۰۰ تومان، بستهٔ `TOKEN_50` با ۱۲٪ تخفیف ۲۲۰٬۰۰۰ تومان است. برای هر خرید تازه یک `Idempotency-Key` جدید بفرستید. برای تکرار همان درخواست پس از قطع ارتباط از همان کلید استفاده کنید. نتیجهٔ پرداخت در `data.status` با `SUCCEEDED` یا `FAILED` مشخص می‌شود. خرید ناموفق در تاریخچه می‌ماند و `token_delta` آن صفر است.

`WALLET_MOCK_RANDOM_ENABLED=true` احتمال موفقیت را از `WALLET_MOCK_SUCCESS_PERCENT` می‌خواند که مقدار نمونهٔ آن ۷۵ است. برای تست قطعی می‌توانید در همین حالت درصد را روی `0` یا `100` بگذارید. با `WALLET_MOCK_RANDOM_ENABLED=false` همهٔ خریدهای جدید آزمایشی موفق می‌شوند. پس از تغییر `.env` برنامه را دوباره اجرا کنید.

هدیهٔ کیف پول ۳ توکن و فقط یک بار برای هر حساب است. پنج شرط شامل نام و نام خانوادگی، عکس پروفایل، ایمیل تأییدشده، شمارهٔ تأییدشده و اتصال تلگرام است. پس از تکمیل، سابقه با نوع `REWARD` و کد `PROFILE_COMPLETION` ثبت می‌شود. ثبت‌نام با موجودی صفر شروع می‌شود. این صفحه فعلاً فرایند خرید شبیه‌سازی‌شده و هدیه را پوشش می‌دهد و مصرف توکن برای پرمیوم‌کردن اکیپ خارج از محدودهٔ فعلی کیف پول است.


درخواست HTTP در Router به Handler می‌رسد و پس از اعتبارسنجی به سرویس کاربردی می‌رود. سرویس قواعد دسترسی و عملیات را اعمال می‌کند و داده را از طریق قراردادهای دامنه و پیاده‌سازی Repository می‌خواند یا تغییر می‌دهد. تغییرهای چندمرحله‌ای در سرویس‌ها با تراکنش مدیریت می‌شوند.

| بخش | فناوری |
| --- | --- |
| API و احراز هویت | Go، Gin، JWT و Google OAuth/OIDC |
| پایگاه داده | PostgreSQL 15، GORM، pgx و Goose |
| کش و وضعیت موقت | Redis 7 و go-redis |
| فایل‌ها | RustFS با API سازگار با S3 |
| ارسال پیام | RabbitMQ، workerهای مستقل و SMTP |
| توسعه و مستندات | Viper، Docker Compose، GNU Make و Bruno |

برای ساخت نسخهٔ HTML کالکشن با همان دستور استفاده‌شده در CI، ایمیج مستندات را از ریشهٔ مخزن بسازید. پورت `8081` در این مثال برای مشاهدهٔ داک است.

## عیب‌یابی محلی

| نشانه | وضعیت را چطور بررسی کنیم |
| --- | --- |
| `required variable RUSTFS_API_PORT ...` | هر دو کلید `RUSTFS_API_PORT` و `RUSTFS_CONSOLE_PORT` را در `.env` مقداردهی کنید. |
| `ECONNREFUSED` در Bruno | سرور و پورت واقعی را در خروجی `make run` ببینید. ابتدا `/health` را بزنید و سپس `baseUrl` را در محیط فعال برونو بررسی کنید. |
| `Application is already running` | از ترمینال دوم در همان checkout، `make stop` را اجرا کنید. `make down` برای کانتینرهاست و Go روی میزبان اجرا می‌شود. |
| جدول یا ستون پیدا نمی‌شود | `go run ./cmd/migrate status` را بررسی کنید و مایگریشن‌های باقی‌مانده را با `up` اعمال کنید. اگر Goose نسخهٔ قدیمی یا مایگریشن جاافتاده گزارش داد، ابتدا تاریخچهٔ دیتابیس و شاخهٔ فعلی را تطبیق دهید. |
| `401 INVALID_CREDENTIALS` | ایمیل و رمز همان حساب را بررسی کنید. هر محیط به دیتابیس و seed خودش متصل است. ورود موفق روی لوکال وجود همان حساب روی سرور تیمی را تضمین نمی‌کند. |
| `401 TOKEN_EXPIRED` | `Refresh Token` را بزنید یا دوباره وارد شوید. محیط فعال باید توکن جدید همان حساب را داشته باشد. |
| OTP ایمیل به صندوق نمی‌رسد | در حالت تست ترمینال بک‌اند را بررسی کنید. برای SMTP واقعی، تنظیمات فرستنده، اتصال RabbitMQ و خروجی worker ایمیل را بررسی کنید. |
| `503 WALLET_PRICE_UNAVAILABLE` | با حساب ادمین نرخ مثبت ثبت کنید و `List Wallet Offers` را دوباره اجرا کنید. |

## همکاری در توسعه

- برای هر قابلیت یا اصلاح، از `develop` به‌روز شاخه بگیرید و Pull Request را به `develop` بفرستید. انتشار به `main` از طریق Pull Request و بازبینی انجام می‌شود.
- پیام کامیت را با Conventional Commits و scope بنویسید. نمونهٔ مناسب `feat(wallet): add mock token purchases` است.
- برای تغییرات اسکیمای دیتابیس، یک فایل SQL جدید با نسخهٔ زمانی یکتا در [migrations](migrations) بسازید و بخش‌های `Up` و `Down` را طبق نمونهٔ پروژه مشخص کنید. برای اسکیمایی که قبلاً در محیط مشترک اعمال شده، تغییر بعدی را در مایگریشن تازه بنویسید.
- برای تغییر API، درخواست و مستندات برونو، نمونهٔ موفق و خطاها را در همان تغییر به‌روز کنید. تنظیمات جدید را با نمونهٔ قابل استفاده در `.env.example` بنویسید.
- قبل از PR، بررسی‌های Go را اجرا کنید. CI علاوه بر این بررسی‌ها، اسکن اسرار و آسیب‌پذیری‌ها و ساخت ایمیج‌ها را هم اجرا می‌کند. [بررسی‌های CI](.github/workflows/CI-QualityGate.yml) و [گردش کار ساخت](.github/workflows/CI.yml)
